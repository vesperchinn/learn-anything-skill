# 项目模式参考

设计综合项目的参考文档。供 `core/prompts/project-design.md` 使用。

## 好项目的标准

一个好的综合项目具备以下特征：

1. **真实**：它做的是真正有用的事情，哪怕很小
2. **完整**：有开始、中间和结束——不是一个片段
3. **可验证**：成功可以客观衡量（能运行/能编译/能产出结果）
4. **可展示**：学习者会自豪地拿出来给别人看
5. **小巧**：按学习者的每日时间预算，7 天内可完成

## 按领域类型的项目模式

### 模式 A：造工具（技术类领域）

**适用**：编程、AI/ML、DevOps、安全、数据工程

**模板**：造一个不大但能用的小工具，解决一个真实问题。

**示例**：学习 AI Agent → 造一个个人研究助手，自动收集并总结某个主题的信息。

**交付物**：可运行的代码、带使用说明的 README、演示视频或截图。

---

### 模式 B：建框架（概念类领域）

**适用**：产品管理、设计、战略、方法论

**模板**：创建一个结构化的框架、操作手册或决策树。

**示例**：学习产品管理 → 制作一个产品需求模板，附带优先级排序矩阵和干系人检查清单。

**交付物**：框架文档、将该框架应用于真实案例的完整示例。

---

### 模式 C：做内容（知识类领域）

**适用**：写作、历史、哲学、科学传播

**模板**：产出一篇高质量的深度内容，展示深刻理解。

**示例**：学习营养学 → 写一份 7 天饮食计划，附带营养分析、购物清单和循证引用。

**交付物**：发布的内容作品、引用来源、纳入同行反馈。

---

### 模式 D：分析数据（研究类领域）

**适用**：数据科学、经济学、社会学、市场研究

**模板**：收集、清洗、分析和可视化一个数据集，回答一个具体问题。

**示例**：学习数据分析 → 用公开电商数据搭建一个销售仪表盘，包含趋势分析和建议。

**交付物**：分析笔记本/报告、可视化图表、可执行的洞察。

---

### 模式 E：设计系统（工程类领域）

**适用**：系统设计、架构、网络工程、SRE

**模板**：设计一个满足特定需求的系统，附带架构图和权衡分析。

**示例**：学习系统设计 → 设计一个短链接服务，包含可扩展性分析、数据库方案和 API 设计。

**交付物**：架构图、设计文档、权衡分析、容量估算。

---

## 项目规模计算公式

```
项目规模 = (每日可用小时数 × 7 天) × 0.7

0.7 的系数用于预留学习、调试和迭代的时间。
```

| 每日时间 | 7 天项目预算 | 推荐模式 |
|---------|-------------|---------|
| 1 小时/天 | 约 5 小时 | 单一功能工具、简短框架、单次分析 |
| 2 小时/天 | 约 10 小时 | 多功能工具、完整框架、数据集分析 |
| 4 小时/天 | 约 20 小时 | 全栈小型应用、全面框架、多分析报告 |

## 无代码替代方案

对于没有编程基础的学习者，可以改造技术类项目：

| 原方案 | 替代方案 |
|-------|---------|
| 搭建一个应用 | 设计一份详细的系统规格说明书 + Figma 原型图 |
| 写一个脚本 | 记录一份逐步操作的手工工作流程文档 |
| 训练一个模型 | 整理一个数据集，附带标注规范说明 |
| 搭建一个仪表盘 | 创建电子表格模板，手动分析数据 |

## 项目质量检查清单

在最终确定项目设计之前，逐项确认：

- [ ] 所有 20% "必须学"的核心概念都得到了练习
- [ ] progress.md 中记录的学习者前 3 个薄弱点已被覆盖
- [ ] 每天都有具体、可验证的交付物
- [ ] 最终成果能在 5 分钟内完成演示
- [ ] 已预判可能的失败模式（每天附上常见陷阱说明）
- [ ] 存在升级路径——项目结束后如何继续改进
